BubuDry Technical Documentation

Complete reference for the Hoover HLE C10TG tumble dryer dashboard.
Covers architecture, data sources, API mapping, edge cases, and deployment.

Overview

BubuDry is a single-file Python web application that monitors a Hoover/Candy tumble dryer via the hOn cloud API (using the pyhOn library) and presents a dark-mode dashboard accessible from any browser on the local network.

Architecture

Raspberry Pi +----------------------------------------------+ | polling_loop() (background thread) | | | | | | every 30s: asyncio.run(fetch_full_state) | | | | | | | +-- pyhOn ---> hOn Cloud API | | | | (HTTPS) (auth, appliance data) | | | | | | | +-- parse_dryer_state() | | | +-- load_statistics() | | | +-- load_command_history() | | | | | +---> shared state{} dict (with lock) | | | | Flask web server (main thread, port 5000) | | GET / --> HTML dashboard | | GET /api/state --> JSON state snapshot | | POST /api/command -> send command to dryer | | | +----------------------------------------------+ | | HTTP (LAN) v +------------------+ | Browser (laptop, | | phone, tablet) | | polls /api/state | | every 10 seconds | +------------------+
Important: No MQTT
Despite the original design intent, BubuDry uses HTTP polling only, not MQTT. The pyhOn library's MQTT support is experimental and unreliable on Raspberry Pi. Status updates therefore have a latency of up to POLL_INTERVAL seconds (default 30).

Data Flow

Polling Loop

A daemon thread runs polling_loop() which:

  1. Calls asyncio.run(fetch_full_state()) — creates a fresh event loop each cycle
  2. _get_dryer() returns (or creates) the hOn session and finds the tumble dryer appliance (type "TD")
  3. dryer.load_attributes() refreshes all parameters from the cloud
  4. parse_dryer_state() extracts a flat dictionary from the pyhOn appliance object
  5. Statistics, command history, and available programmes are loaded via separate API calls (each wrapped in try/except so a failure doesn't kill the poll)
  6. The result is written to the shared state dict under state_lock

State Machine

The dryer's machMode parameter maps to UI states:

+-------+ Start +----------+ | Off | ------------> | Running | --+ | (0) | | (1,2,6,7)| | +-------+ +----------+ | Pause ^ | v | | +----------+ | Finished | | Paused | +---- +----------+ <----+ | (3) | | Finished | +----------+ | (4, 5) | | +----------+ | Resume v +----------+ | Running | +----------+ At any state: water_tank_full or filter_dirty --> Error / Attention errors != 0 --> Error connection lost --> Unknown / Reconnecting

Reconnection Logic

Failure #ActionWait
1st Keep existing session, retry quickly. Token refresh attempted on next _get_dryer() call. min(30, POLL_INTERVAL/2) seconds
2nd+ Destroy session (_hon = None), force full re-login on next attempt. POLL_INTERVAL seconds
Any failure UI state is cleared to Reconnecting... so stale "Running" is never shown. —

Controls Logic

  • Start — visible when status is off, finished, or unknown AND connected is true. Sends startProgram with the currently selected dryLevel.
  • Pause / Resume — visible when running or paused AND connected. Toggles between pauseProgram and resumeProgram.
  • Stop — visible when active (running/paused) AND connected. Shows a confirm() dialog before sending.
  • Dryness — visible when dryer is off/finished AND connected. Opens a pop-up picker for Iron/Hang/Cupboard/Extra dry. Only affects the next start command.

Known Edge Cases & Bugs

Bugs Fixed in Audit (2026-03-18)

1. Stale "Running" status after disconnection

Problem: When the polling loop caught an exception, it set state["connected"] = False but left state["status"] as-is. The UI would show Running with "Dryer offline" indefinitely.

Fix: On poll failure, status is now explicitly reset to "unknown" and status_label to "Reconnecting...".

2. Water tank alert silently overwritten by filter alert

Problem: The priority override logic ran sequentially: if water_tank: ... if dry_filter: .... When both were true, only the filter message was stored in error_msg.

Fix: Both conditions are now collected into a list and joined with " | ". The frontend also renders them as separate alert banners (water_tank_full and filter_dirty are separate booleans).

3. _hon_lock declared but never used

Problem: A threading lock for the hOn session existed but was never acquired. The polling thread and Flask command handler could race on the _hon global — e.g., one sets _hon = None while the other is mid-API-call.

Fix: _get_dryer() and the reconnect path now acquire _hon_lock.

4. Aggressive reconnection killing sessions

Problem: On the very first poll failure, the code set _hon = None, forcing a full re-login. This is slow (~3-5s) and can hit hOn rate limits.

Fix: First failure retries quickly without destroying the session. Auth token refresh is attempted. Only after 2+ consecutive failures is the session destroyed.

5. Missing machMode 6

Problem: MACH_MODE_MAP had codes 0-5, 7 but not 6. Mode 6 ("Delayed Start") would show as "Mode 6" / unknown.

Fix: Added 6: ("running", "Delayed Start").

6. Unused imports

Problem: json, Response, and send_from_directory were imported but never used.

Fix: Removed.

7. Docstring claimed MQTT support

Problem: Module docstring said "Real-time MQTT status updates" but the app only polls HTTP.

Fix: Updated docstring to accurately describe polling-based architecture.

8. systemd service hardcoded credentials

Problem: bubudry.service had Environment="HON_EMAIL=..." lines that needed manual editing, even though .env support was added.

Fix: Service file now relies on python-dotenv reading from .env.

Known Limitations

Start command sends no programme

The "Start" button calls sendCommand('startProgram') without a programme name. This relies on the dryer/pyhOn using a default programme. If no default exists, the command may fail or be rejected. A programme picker could be added if needed.

lastConnEvent can be stale

The dryer's online/offline status comes from lastConnEvent.category. This event may not update in real-time — the dryer could lose Wi-Fi without pushing a "DISCONNECTED" event. The green dot may show "connected" even when the dryer is actually unreachable.

No command debounce

Rapid button clicks will send multiple commands. The 1.5s refresh delay after a command helps but doesn't prevent it. For an elderly user this is unlikely to be an issue.

asyncio.run() per request

Both the polling loop and Flask command handler call asyncio.run(), which creates a new event loop each time. This works correctly but is slightly wasteful. A persistent event loop running in a dedicated thread would be more efficient, but adds complexity not justified for this use case.

Potential Issues to Watch

hOn API rate limiting

Polling every 30 seconds makes ~2,880 API calls/day. Haier/Candy's hOn backend does not publicly document rate limits. If they throttle, increase POLL_INTERVAL to 60 or 120.

hOn API authentication changes

The pyhOn library reverse-engineers the hOn mobile app's API. Authentication flow can break when Haier updates their backend. Keep pyhon updated (pip install --upgrade pyhon). Facebook-authenticated accounts may have intermittent issues — a direct email/password hOn account is more reliable.

Memory on Raspberry Pi

Flask + pyhOn + aiohttp (pyhOn dependency) typically use ~60-80 MB RSS. Well within the 1 GB Pi's capacity, but avoid running other heavy services alongside it.

Tab switching fragility

The switchTab() function matches tabs by comparing btn.textContent.toLowerCase() with the tab name. If the tab button text is ever changed (e.g., abbreviated for mobile), the matching will break. This could be improved with data-tab attributes.

Deployment

Setup Instructions

# On the Raspberry Pi:
cd /home/pi
git clone <your-repo> bubudry   # or scp the files across
cd bubudry

# Create virtual environment
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

# Create credentials file
cat > .env << 'EOF'
HON_EMAIL=your@email.com
HON_PASSWORD=your_password_here
EOF
chmod 600 .env   # restrict permissions

# Test it works
python app.py
# Open http://raspberrypi.local:5000 in a browser

systemd Service

# Install the service
sudo cp bubudry.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable bubudry    # start on boot
sudo systemctl start bubudry     # start now

# Useful commands
sudo systemctl status bubudry    # check if running
journalctl -u bubudry -f         # live log tail
sudo systemctl restart bubudry   # restart after changes
