BubuDry Technical Documentation

This document reflects the current codebase behaviour in app.py. It replaces older notes that described a pure polling model and older timing defaults.

BubuDry now runs in a hybrid model: MQTT push updates when available, with periodic heartbeat polling and slower enrichment calls for history/statistics.

Runtime Architecture

  • Flask thread serves the dashboard and API endpoints.
  • Background poller thread owns a persistent asyncio event loop.
  • Persistent hOn session is reused and protected by _hon_lock.
  • Shared state dict is guarded by state_lock.

Data Flow

1) Quick state path

  1. fetch_quick_state() calls dryer.load_attributes().
  2. parse_dryer_state() maps raw appliance values into UI-ready fields.
  3. Results are written to state and status transitions are logged.

2) Slow enrichment path

Every SLOW_POLL_INTERVAL, BubuDry fetches maintenance/statistics, command history, and available start programmes.

3) Push updates path (preferred)

On first successful connection, BubuDry attempts hon.subscribe_updates(on_push). If supported by installed pyhon, state updates are applied immediately on MQTT events.

4) Fallback path

If push updates are unsupported or reconnection occurs, the app falls back to standard quick polling.

Frontend Behaviour

  • UI polls /api/state every 2 seconds.
  • After sending a command, UI performs an extra refresh after 1.5 seconds.
  • Controls include start, pause, stop, programme picker, and dry-level picker.
  • Tabs display live status, cycle history, and usage/maintenance statistics.
The JS comment in app.py previously said “every 30 seconds” while code polled every 2 seconds. This documentation now reflects the actual runtime value.
